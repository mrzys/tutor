# 导入问题处理 UI/UX 设计提案 Review

日期：2026-10-27

评审对象：`C:\Users\mrzys\.codex\visualizations\2026\10\27\import-issue-triage-design\导入问题处理-UIUX设计提案.html` 与 `review-layout.png`

核对范围：提案全部文字、效果图，以及当前 `ImportPaper.tsx`、`ImportPaper.css`、`import-review.ts`、后端入库资格、发布与教学稿控制合同。

## 结论

**方向通过，建议“补齐合同后实施”，不建议直接按效果图开工。**

提案最有价值的不是黄／红颜色，而是把“原题是否可入库”与“AI 解析是否可采用”拆开，并允许合格内容先入库、其余问题继续保留。这与当前数据结构和安全边界基本一致。方案也正确避免了整卷重跑、一键清除疑点、自动循环复核和把模型意见当成数学事实。

但还需补齐四个闭环：

1. 原题入库后的解析继续处理与后续补发布；
2. 状态命名、颜色优先级和计数口径；
3. “仅原题入库”按钮与批量确认的实际操作路径；
4. 问题到句段的稳定定位合同。

## 一、提案中应保留的设计

### 1. 原题与解析分轨是正确核心

提案第 5、6、11 行明确区分“原题已核对／AI 稿待核”，并说明仅原题入库不会采用错误 AI 稿。效果图也用“原题·提取完整”和“AI 解析·未采用”两个独立标识表达，避免一个“合格／不合格”覆盖整道题。

这与当前后端已有能力一致，而不是需要推翻现有发布规则：

- `review.rs:78-80`：教师人工核对路径由 `reviewDecision` 与 `check_approved` 判定；只有模型自动放行路径在 `review.rs:59-70` 额外要求 `teaching::ready(q)`。
- `imports.rs:1805-1814`：发布清单可纳入教师已核对题。
- `teaching.rs:1362-1365`：教学稿未 ready 时直接返回，不写入 `teachingAnalysis`。

因此，“教师核对原题后仅原题入库”已有后端基础。提案应明确复用这一事实，避免实施者误以为要放宽教学稿放行条件。

### 2. 问题清单比日志更适合教师

左栏采用“题号＋主题＋原题／解析＋一句原因”，右栏先解释问题再提供动作，符合教师处理顺序。效果图没有暴露哈希、错误码和原始响应，技术细节放入折叠区，层级合理。

### 3. 操作与阶段绑定，边界表述准确

提案第 6、7 行正确区分：

- 技术失败可显式重试；
- 首次复核与“已复核一次仍有问题”不是同一动作；
- 已复核后不出现无条件“再复核”；
- 模型重生成若将来提供，必须是单独显式任务；
- 查看页面不自动调用模型；
- 原回复、旧尝试与额度记录保留。

这些约束应原样进入验收标准，不能只保留按钮文案。

### 4. 不提供“一键忽略全部”

逐项核对、保留原始意见、绑定候选版本、填写依据，与当前 `import-review.ts:130-152` 的显式 acknowledgement／patch 合同一致。尤其是“误报仅保留为提醒”而不是删除历史意见，方向正确。

### 5. 视觉层级与可访问性原则合理

效果图的当前题选中态、右侧主按钮、原题与 AI 稿分区都清楚；红色同时配图标和文字，不仅依赖颜色。提案还覆盖窄屏、44px 点击区域、公式／图／表滚动、未保存离开确认，符合 `docs/design/tutor-ui.md` 的共享规范。

## 二、实施前必须补齐的问题

### P1：原题入库后的解析生命周期没有闭环

提案第 11 行承认“原题已入库”和“解析仍待核”可以同时存在，但没有说明此后如何完成解析、如何再把合格解析加入题库已有题。

当前实现不能承担这个后续流程：

- `ImportPaper.tsx:272`：题目 published 后，`needsOpinion` 直接为 false，问题面板隐藏。
- `ImportPaper.tsx:730、1579`：已发布题的教学稿核对和局部修订被禁用。
- `controls.rs:176-177`：后端同样拒绝已发布题通过现有教学复核控制入口改写。
- `ImportPaper.tsx:275` 与 `teaching.rs:1026`：已有任何发布题后，现有继续教学处理路径受限。

**需要新增明确设计：**

1. 仅原题入库后，已发布的原题版本保持不可变；本地导入记录可继续保留并处理独立教学草稿。
2. 教学草稿就绪后，提供单独的“更新题库解析”动作与确认弹窗，不把它伪装成首次入库，也不自动覆盖题库。
3. 补发布需绑定题库题目的 `contentVersion`／`teacherVersion`、当前原题哈希与候选哈希；版本冲突时要求重新核对。
4. 明确补发布成功后状态为“原题已入库／解析已采用”，失败时原题与本地草稿均保留。
5. 若首版不做补发布，应把“原题已入库后仍继续处理解析”列为暂不支持，避免制造永远无法完成的待办。

这是本提案最重要的范围补充。

### P1：状态体系需要从文案升级为可计算投影

当前提案同时使用：

- 标签页“待处理 8”；
- 黄色子状态“6 待处理”；
- 红色子状态“2 需核对”。

同一个“待处理”既表示全部待办，又表示黄色子集，容易让教师误以为数字矛盾。建议将总标签改为 **“待办”** 或 **“未完成”**，黄色保留“待处理”，红色保留“需核对”。

还需给出确定的状态聚合规则：

- 任一未解决的实质原题／数学问题 → 红；
- 无红色问题但存在技术失败、未开始、未完成或可编辑工作 → 黄；
- 重复 → 独立中性状态，不计失败；
- 已人工核对并转为 informative 的提醒 → 保留记录，但不再计待办；
- 原题发布状态与教学待办分别计数，不用单一 `eligible` 推导全部颜色。

效果图第 7 题是黄色“解析·解法需调整”，而状态表把数学推导／证明问题归为红色。“解法需调整”若指核心方法或推导缺陷，应改红；若只是表达问题，应改为“讲解需调整”或“表达待核”。

建议后端投影至少提供：

```text
sourceState: pending | eligible | blocked | published
teachingState: not_started | generating | failed | needs_review | ready | adopted | not_adopted
openIssueCounts: { actionable, substantive }
duplicateState: none | exact
```

前端只渲染投影，不从黄／红颜色反推发布资格。

### P1：“核对原题后，仅原题入库”动作语义不清

效果图中的按钮容易被理解为一次点击就完成“核对＋发布”，但提案又要求完成多项原题核对，页头还存在统一“确认入库（10）”。

建议首版采用明确的两阶段流程：

1. 右栏按钮只叫 **“核对原题”**，打开现有人工核对区；
2. 核对保存后，由后端重新计算资格；
3. 页头统一确认弹窗逐项列出“仅原题／含已采用解析”；
4. 发布时后端重新判定每题内容范围，前端不能自行声明某题可仅原题入库。

若产品确实需要单题立即发布，也必须另有单题确认弹窗，不能与统一批量入口混用同一含糊按钮。

### P1：句段定位缺少稳定身份

提案第 4 行要求“选中问题后定位相关句段”，这是提升效率的关键，但当前通用 `TeachingIssueRow`（`import-review.ts:81-89、111-119`）只保证 `issueIndex`、原文字符串、哈希和 disposition，并不能保证所有疑点都有句段位置。

建议问题投影增加可选的精确目标：

```text
target: {
  domain: "source" | "teaching",
  fieldPath: "teachingSolution" | "stem" | "...",
  segmentId?: string,
  candidateSha256?: string,
  sourceContentSha256?: string
}
```

约束：

- 有稳定目标时滚动并高亮对应句段；
- 只有字段信息时定位到字段，不假装精确到句；
- 无位置或候选已变化时显示“无法定位到原句段”，保留问题文本；
- 不用模糊搜索第一句相似文本冒充定位；
- 编辑、重生成或句段重编号后，旧高亮必须失效并重新计算。

### P2：计数与批量选择口径需一致

效果图为“全部 19／待处理 8／已入库 0／确认入库 10”。余下 1 道可能是重复题，但图中没有显示，用户需要自行做算术。建议在模拟数据中直接增加“重复 1”，或把可入库数改为 11，并注明各过滤器允许重叠。

提案第 12 行写“批量操作只作用于明确选中的合格范围”，但效果图没有勾选控件，页头数字又表现为全部合格题。首版建议不引入选择系统：**按钮表示全部当前可入库题，确认弹窗给出精确题号清单**；若坚持“明确选中”，则必须补选择态、全选规则和计数规则。

计数还需明确：

- “待办”可以包含“原题已入库／解析待核”的题；
- “已入库”与“待办”不是互斥分组；
- “可入库数”是当前未发布且符合资格的题数，不是“全部－待办”；
- 重复题不进入失败率，也不能被批量发布误伤。

### P2：把重试确认拆成可验证合同

第 7 行已经写出费用与额度提示，建议进一步固定以下验收点：

- `questionIds` 恰好只有当前题；
- 操作具有 `operationId`，网络重试不重复创建新尝试；
- 明确本次是“只生成”还是“生成＋首次复核”，若包含复核，费用和调用次数分别说明；
- 只锁当前题的相关写操作，其他题可读；是否可编辑须与后端记录级 CAS／后台任务限制一致；
- 超时只表示本地未收到有效回复，不宣称服务商未处理；
- 新响应不继承旧候选的人工核对与补丁授权。

## 三、视觉稿具体评价

### 做得好的部分

- 左栏当前题黑色竖线和浅灰底足够明确，黄／红图标在清单中容易扫描。
- 中栏先原题后 AI 待核稿，符合先核对材料、再阅读生成内容的顺序。
- 右栏问题列表默认只展开第一项，降低信息量，同时保留其他问题入口。
- 主操作“编辑解析”和次操作“核对原题后，仅原题入库”层级清楚。
- 顶部主按钮显示数量，比无范围的“确认入库”更可预期。

### 需调整的部分

- 统一“待办／待处理”的命名，消除 8 与 6＋2 的术语重叠。
- 修正第 7 题“解法需调整”的颜色或文案。
- 补出重复题的计数或条目，解释 19、8、10 的关系。
- “原题·提取完整”不等于“原题已人工核对”，正式实现必须继续区分这两个事实，不能复用同一成功文案。
- 效果图不能证明真实公式、长题干、大表格和题图在三栏下仍然可读；实施时需用真实广安卷、天津卷等长材料验收，而非沿用图中简化题文。

## 四、建议的实施拆分

### 第一阶段：只读投影与导航，不新增模型调用

- 原题／解析双状态；
- 待办、全部、已入库、重复过滤；
- 黄／红问题清单与多问题展开；
- 稳定目标定位及降级行为；
- 真实资格驱动的计数与确认清单。

### 第二阶段：人工处理闭环

- 复用原题核对、教学字段局部编辑、版本校验与逐项 acknowledgement；
- 编辑后保持待核，直至后端重新投影；
- 处理记录、未保存离开确认与下一待办导航。

### 第三阶段：显式单题技术重试

- 精确单题目标、费用确认、幂等和审计；
- 不自动追加复核，不重置额度，不整卷重跑。

### 第四阶段：原题已入库后的解析补发布

- 本地教学草稿继续处理；
- 题库已有题的版本绑定与单独更新确认；
- 失败保留、冲突重核和成功后的双完成状态。

若希望控制首版范围，第四阶段可以暂缓，但必须在 UI 文案中明确“仅原题入库后，本页暂不能继续补解析”，不能展示一个实际走不通的待办流程。

## 五、最低验收清单

1. 数学问题未解决时，仅原题入库的题库结果不含 `teachingAnalysis`。
2. 仅原题入库后，该题仍出现在解析待办中；已发布原题不可被本地后续编辑覆盖。
3. 后续解析补发布只更新明确确认的题库解析，版本冲突时不覆盖。
4. 任一红色问题存在时整题显示红；仅有技术重试工作时显示黄；重复不显示红。
5. informative 提醒保留在历史中，但不继续计入未解决待办。
6. 19／8／10／重复／已入库等数字均由同一投影计算，过滤器重叠规则有文案说明。
7. 点击每个问题只定位其授权目标；无稳定位置时明确降级，不误高亮。
8. 单题重试的审计目标只有该题，旧尝试不变，查看页面不产生调用。
9. 批量确认弹窗精确列出每题是“仅原题”还是“含解析”，发布时后端重新验证。
10. 真实长题干、KaTeX、表格和题图在宽屏、容器变窄及手机布局下无遮挡；键盘焦点、44px 目标和未保存离开确认通过实际测试。

## 最终意见

**保留整体信息架构与安全边界，先补“入库后解析生命周期”和状态／动作合同，再进入实施。** 这份提案已经适合作为 UI 方向稿，但还不足以直接充当开发验收合同。尤其不要把现有“教师核对可仅原题入库”误改成“教学稿也必须 ready”，也不要在未设计补发布流程前承诺“入库后仍可继续完成解析”。
