- 草稿的“确认成卷与输出”移至工作区底部右侧，左侧只显示当前题量、分值（计分时）和自动保存状态。

## 实际数据与边界

只读查询生产 SQLite，当前仅有一份 10 题草稿及一份成卷，样本量不足以代表长期分布。

| 阶段 | 此次模型耗时 | 结果 |
| --- | --- | --- |
| 需求整理 | 2.214 秒 | 成功 |
| 蓝图规划 | 10.918 秒 | 第二次尝试成功 |
| 两批候选比较 | 13.742 + 4.102 秒 | 两批成功，顺序执行 |
| 教学覆盖复核 | 9.056 秒 | 两次尝试均未通过输出校验 |

确认蓝图后的候选比较及覆盖复核合计模型等待 26.9 秒，不包含数据库读取、组合或网络传输。当前代码先逐批排序、再整卷组合、再同步复核。可以后续将相互独立的候选比较限制为两批并发，仍在全部排序后统一去重。复核不能与最终选题并行，且本次失败原因需另行检查。

真正“确认并保存成卷”的代码路径不调用模型，也不自动生成 PDF。不可将上述 26.9 秒归因于保存接口。保存接口未取得独立线上端到端计时，不能宣称其耗时已查明。

草稿 JSON 3,238,780 字节、成卷 JSON 3,244,535 字节；在服务器对同一份数据做 gzip level 4 分别为 457,214 / 458,631 字节，缩小 85.9%，压缩分别约 39.2 / 39.4 毫秒。这是数据压缩测量，并非某次浏览器实际下载耗时。

闲时服务器内存 1,613 MB，可用约 639–659 MB，交换内存使用为 0；CPU 约 99% idle，应用内存约 174 MB。仅能说明采样时没有资源耗尽，不能排除组卷/PDF 并发时的峰值。SSH 曾间歇连接超时，需与模型等待区分。现有证据不足以把慢归咎于服务器规格。
